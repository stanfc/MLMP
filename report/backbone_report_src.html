MLMP · Phase U · five done, fourteen in flight

Does the gate survive a change of backbone?

AdaGate’s threshold is unitless, so it should not care which visual encoder it sits on. That prediction has now been tested on five backbones for a full 150 rounds each. All five behave identically: the ungated arm collapses, the gated arm holds, and the firing rate lands in the same narrow band without anything being re-tuned.

Why this experiment

The gate’s selling point is a threshold that never needs re-tuning

The trigger is a robust z-score of the grad-norm slope against its own recent spread, and the restore depth is an ECDF rank. Neither is expressed in units belonging to a dataset, an objective, or an encoder. That predicts one number, trend_thr = 0.5, should produce the same duty cycle everywhere.

Two axes already support it: across datasets the firing rate is 0.292 / 0.315 / 0.299, and across objectives 0.292–0.310 — a 1.06× spread over five published losses. The backbone is the obvious third axis, and it was empty.

Every ungated arm shows the same climb–peak–collapse shape and ends 13 to 26 mIoU below its gated twin. Every gated arm reaches its plateau early and then does not move: ClearCLIP ViT-L/14 peaks 32.09 at round 81 and finishes 31.91; ClearCLIP ViT-B/16 peaks 31.20 at round 43 and finishes 31.18; NA-CLIP ViT-B/16 peaks 31.08 at round 81 and finishes 31.08; NA-CLIP ViT-B/32 peaks 28.21 at round 121 and finishes 28.17.

The number the campaign was actually run for is the last one. Across the five encoders the gate fires on 0.282 / 0.295 / 0.296 / 0.299 / 0.300 of windows — a 1.06× spread, which is the same spread the five published objectives gave, and nobody chose it. Pooling all three transfer axes, thirteen runs spanning three datasets, five objectives and five encoders sit between 0.282 and 0.315: a 1.12× total spread on one unitless constant.

Before any arm finished

Three things the setup work turned up

None of these were the point of the experiment. All three matter more than the arms themselves, and the first is the kind of thing a reviewer finds if we don’t.

Affects a published number

The no-adaptation floor of 23.34 was measured with a different prompt setting than every adapted run

23.341 prompt · historical
28.217 prompts · matched
+4.87gap

Both no-adapt runs on disk pass an empty --prompt_dir, which falls back to the single template "a photo of a {}". Every adapted run — the flagship and all five plug-and-play arms — passes --prompt_dir prompts.yaml, the 7-template ensemble. Re-running no-adapt with the ensemble gives 28.21; re-running it with one prompt reproduces the historical 23.89 / 22.09 / 23.85 / 23.53 / 23.34 exactly. That isolates the prompt as the only variable, and verifies the harness at the same time.

The within-objective Δ columns are unaffected — gate and no-gate always share a prompt setting. What changes is the secondary “is it above the no-adapt floor?” column of the plug-and-play table. Against 28.21, only Ours (31.92) is clearly above. DELTA (28.59) becomes marginal; SAR (27.79), MLMP (23.61) and TENT (22.48) fall below.

Would have silently broken the ViT-B arms

top_block_exclude hard-coded the number 24

The exclusion test read block_index >= (24 - top_block_exclude). On ViT-L/14 that is correct: 24 blocks, tbe=6 freezes the top six and 74 of 100 LayerNorm params adapt. ViT-B/16 has only 12 blocks, so 24 - 3 = 21 matches nothing and the flag froze nothing at all. Since this flag is worth about 5.7 mIoU on TENT, an unnoticed no-op would have made the ViT-B arm meaningless.

It now reads encoder depth from the model. Verified against the old logic on both backbones: ViT-L/14 is bit-identical at tbe 0 / 3 / 6 (98 / 86 / 74 params), so all 241 historical runs still reproduce; ViT-B/16 at tbe=3 now gives 38 of 50 — the same fraction of the encoder, which is what “no re-tuning” has to mean across depths.

Latent crash, now fixed

Multi-layer output under arch='vanilla' raised UnboundLocalError

In the visual forward pass, final_x was assigned only in the last-layer branch, so asking a vanilla-architecture model (SCLIP, plain CLIP) for intermediate layers crashed outright. It had never surfaced because those two have only ever run with vision_outputs=(-1,), and MLMP’s 18-layer UAML has only ever run on arch='reduced'.

With the fix it runs — and then tells us something worth keeping. SCLIP on ViT-B/16 scores 6.61 mIoU with a 9-layer UAML, against a 26.54 zero-shot floor. arch='reduced' exposes the attention branch at each depth, which stays in the text-aligned space, so averaging depths is meaningful; arch='vanilla' exposes the full residual stream, and averaging that across nine depths destroys the alignment. So the method carries a real, statable scope condition: it needs an OVSS formulation exposing reduced dense features at multiple depths. NA-CLIP and ClearCLIP do; SCLIP and vanilla CLIP do not.

Arm selection

Which backbones are fair targets, decided by measurement rather than preference

Ten zero-shot configurations were measured first, at roughly 30 s each, under the matched 7-prompt protocol. Two candidates were then eliminated on the evidence: SCLIP at ViT-L/14 (15.51) and vanilla CLIP at either scale (3–5) sit so far below everything else that adapting from them would measure the backbone’s brokenness rather than the gate.

Results, in flight

Four backbones, one unchanged configuration

Every arm is the flagship command with only the backbone-dependent quantities changed: the encoder itself, top_block_exclude, and the UAML depth — the latter two held at the same fraction of the encoder (24 blocks → 6 and 18 layers; 12 blocks → 3 and 9). Learning rate, base_rst, trend_thr, lag_mode and every DeYO/MLMP hyperparameter are untouched. Each arm carries its own no-gate control at --base_rst 0.0.

The claim under test

Duty cycle is the number to watch, not mIoU

The prediction was that the backbone arms would land in the band the dataset and objective axes already occupy, without anyone choosing it. They did: 0.282 (ViT-B/16), 0.295 (ViT-B/32), 0.296 (NA-CLIP ViT-L/14), 0.300 (ClearCLIP ViT-L/14). ViT-B/16 is the low end and sits just under the published 0.292–0.315 band; the two ViT-L/14 encoders are inside it. This is the third independent axis, and it is the cleanest of the three.

Status

Nine more backbones, and a scheduler that packs the cards

Five pairs are finished at round 150. Fourteen more arms are running concurrently, covering four OVSS formulations that did not exist in this codebase two hours ago, plus a resolution variant and the seed-variance runs.

SCLIP has been rescued. Its earlier 15.51 was blamed on the backbone; it was actually the output branch. SCLIP's attention paired with arch='reduced' — so the dense features come from the text-aligned attention branch rather than the full residual stream — scores 29.63 at ViT-L/14 and 29.73 at ViT-B/16, the best ViT-B floor measured. That is a 14-point swing from a one-line change, and it confirms the scope condition diagnosed earlier was the right one.

Three of the new formulations now sit above our own default zero-shot: ClearCLIP q-q at 29.97, SCLIP-reduced at 29.63, NA-CLIP Gaussian-only at 29.29, against NA-CLIP's 28.21. The backbone this project has used throughout is not the strongest one available.

__RAIL__

Packing the GPUs was worth measuring, not assuming

The cards are 97.8 GB and a ViT-L/14 arm at batch 1 peaks near 16 GB, so the scheduler now admits a job whenever a card has 22 GB free rather than waiting for the card to be idle. The gain is real and large:

0.57rounds/min · 1 run
3.77rounds/min · 13 runs
4.55rounds/min · 19 runs

Eight times the aggregate throughput of a single job. The cards had been reporting 90–100 % “utilization” the whole time, which only means some kernel was resident — at batch 1 the SMs were mostly idle between launches. But the last step shows saturation arriving: 46 % more jobs bought 21 % more throughput, so this is where the packing stops. Free VRAM is no longer the constraint; compute is.

Two caveats worth stating plainly. This contends for compute with another user's jobs on the same six cards — it is the right trade against leaving 80 GB idle per card, but it is a choice, not a free lunch. And the per-arm wall-clock is now much slower than an uncontended run; the estimate for the fourteen in flight is roughly ten hours.

How to reproduce or refresh this
  • bash bash/backbone_status.sh — scheduler state, every arm's round count, live processes, GPUs, figure timestamps.
  • bash bash/backbone_smoke.sh <gpu> <backbone> [ovss_type] — one-round zero-shot floor for a candidate backbone.
  • bash bash/backbone_ablation.sh list — the arm table; then <arm> <gpu> [rounds] to run one.
  • NEED_MIB=22000 WORKERS_PER_GPU=2 bash bash/job_pool.sh <jobfile> <gpu>... — the scheduler. Appending lines to the job file while it runs works; it re-reads on every pop, and several instances can share one job file safely.
  • python plot_backbone.py — regenerates all three figures plus the md and tex tables. Panels appear as arms produce data and the grid resizes itself.
  • python report/build_report.py — rebuilds this page from report/backbone_report_src.html plus whatever is on disk.
  • kill $(cat save/_backbone_logs/pool.pid) — stops a scheduler; jobs already running continue. Never pkill -f on the script name: the pattern matches the killing shell's own command line.
